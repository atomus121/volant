>
> **v0.5 变更（M2 结题后）**：把 T2 / T6 的验收条件写成**真能重复测量**的形式。①T2 的条件（100 Mbps / 20 ms / 0.1% 丢包）在 Windows 上没有 netem，改用 labserver 的 `grate`/`delay`/`stall_*` 仿真，并写明**没仿真 TCP 拥塞窗口**（偏乐观）；②T6 的「吞吐 = 50 MB/s」拆成「≥ 95%」+「限速那次的请求数不多于全速那次（对比判据）」，因为 planner 分段本身就会重发，小文件上量到 27–39%，与慢盘无关。详见 6.1 与 `docs/m2/REPORT.md`。
>
> **v0.4 变更（M1 结题后）**：T1 的验收口径由绝对「10 GiB ≥ 1.5 GB/s」改为**比值「≥ 同机同条件裸写基线 × 80%」**，并规定测量流程（静置 5 分钟 → 裸写基线 → 引擎 → 裸写基线）。原因是实测发现绝对值量的是 SSD 的缓存状态而不是引擎：同一份代码能测出 1823 / 1477 / 1076 MB/s，裸写对照同步下滑。M1 实测比值 102%，旧口径的 1.5 GB/s 同样也达标。详见 6.1 与 `docs/m1/REPORT.md`。
>
> **v0.3 变更（M0 结题后）**：①UI 框架定为 **egui 0.37**——四个候选框架全部写了原型、同一机器同一视觉规格实测，数据见 7.1；②6.2 内存指标按实测修订（35 MB → 110 MB），并记录「估算值不可当约束」的教训；③**UI 实现推迟到 M4，先只做引擎**，里程碑重排为「引擎核心 → 引擎调优 → 引擎验收 → UI → 扩展 → torrent+打包」；④reqwest 的 TLS 由 rustls 改为 native-tls（rustls 会拖进 aws-lc 的 C 构建崩溃）。
>
> **v0.2 变更**：按你的决策把 torrent 从「延后 v2」提升为 **v1 P0**，明确其实现边界（协议栈用 librqbit，界面「极简 torrent」）；工期由 8 周调整为 10 周；记录 4 项已定决策。

## 0. 一句话

**Volant 是一个只做「把文件从网上下载下来」这一件事的 Windows 下载器：比浏览器快一个量级，比 IDM 干净一个时代，比 MDM 少一半入口。**

> 原句写的是「比 MDM 轻一半」——M0 实测推翻了这个说法：Volant 与 MDM 同为 egui + GPU UI，进程内存处在同一量级（MDM 峰值 106.2 MB，Volant 原型空闲 119.7 MB）。**「轻」不能拿来当卖点，因为它不成立。**能成立的差异是「少一半入口」（顶栏 3 个元素 vs MDM 的 16 个工具栏按钮）、「小一半安装包」、「多一半并发效率」。

反目标（明确不做的事）：

- 不是「万能下载器」。不是视频下载器，不是 NAS 服务端，不是网盘客户端。
- 不是 BitTorrent 协议的实现者。torrent 是 v1 功能，但**协议栈由 librqbit 提供**，Volant 只做调度、落盘与界面——这条边界决定了 torrent 不会变成第二个产品。
- 不是 IDM 的皮肤克隆。不复刻三行 chrome、16 个工具栏按钮、12 列表格。
- 不是功能平权。**宁可少一个功能，不可多一个入口。**

## 1. 第一性原理：下载这件事的物理约束

抛开所有软件形态，"下载"只有一句话：**把远端 N 个字节，按顺序搬到本地磁盘的某个位置**。

决定体验的只有 5 条物理约束，软件只能在其中腾挪：

| # | 约束 | 数学形式 | 后果 |
|---|---|---|---|
| C1 | 链路容量 | 你的宽带，如 500 Mbps ≈ 62 MB/s | 这是吞吐的**硬上限**，软件无法超越 |
| C2 | 单条 TCP 流的吞吐 | `min(rwnd, cwnd) / RTT`，丢包时 cwnd 指数回退 | 100 ms RTT、0.1% 丢包时，单连接往往只有 5–20 Mbps |
| C3 | 服务器策略 | 单 IP 限速、限连接数、限并发 | 有些站点 8 连接＝8 倍，有些站点 8 连接＝被封 |
| C4 | 本地磁盘 | NVMe 顺序写 2–7 GB/s；HDD 顺序 150 MB/s、随机写极差 | 写盘慢会**伪装成网络慢** |
| C5 | 本地 CPU | TLS 解密 + 内存拷贝，单核约 1–3 GB/s | 万兆以下一般不是瓶颈，但会影响小文件延迟 |

**推论（这就是「跑满带宽」的全部真相）：**

1. 因为 C2，**单连接几乎不可能跑满带宽**，必须并发多条流。所需连接数 ≈ 链路带宽 ÷ 单连接可达吞吐。
2. 因为 C3，连接数**不能写死**：要能自动试探、被拒后学习、并按站点记住。
3. 因为 C4，磁盘写必须与网络读**解耦**，否则磁盘抖动会被误判成慢连接，触发错误的重连。
4. 吞吐不是「平均值」，是**木桶效应**：总吞吐 = 所有连接吞吐之和，任何一条连接在等 DNS / 握手 / 请求往返 / 磁盘 flush，这段带宽就永久丢失。
5. 因此「快」= 并发自适应 + 零非网络停顿 + 慢连接让位（把字节重新分配给快连接）。

MDM 的引擎正是围绕这 5 条设计的，这是它「1 GiB 用 1 秒、IDM 用 5.5 秒」的真正原因——不是算法魔法，是**没有浪费任何一次往返**。

## 2. 对标拆解：MDM 是什么

### 2.1 规模事实（决定「全复刻」是否可行）

| 部分 | 代码量 | 说明 |
|---|---:|---|
| `mdm-app`（egui 界面） | 75,859 行 | 20+ 个窗口/对话框，options 单文件 4,511 行 |
| `mdm-engine`（下载引擎） | 14,192 行 | 核心价值所在 |
| `mdm-torrent` | 3,789 行 | 封装 librqbit |
| `mdm-debrid` | 3,311 行 | 3 家网盘账号 |
| `mdm-tools`（yt-dlp/gallery-dl） | 9,703 行 | 外部进程编排 |
| `mdm-cli` / `mcp` / `remote` / `nmhost` / `ipc` | 7,000+ 行 | 自动化与集成 |
| `mdm-labserver`（测试服务器） | 5,296 行 | **基准测试的基础设施** |
| 浏览器扩展（TS/JS） | 3,094 行 | 6 个浏览器 |
| **合计** | **≈ 125,000 行 Rust + 3,000 行前端** | 单人 1–2 年，且大量是**边缘情况**打磨 |

对照组：一个「够用且快」的下载器，引擎 + 界面 + 扩展的合理规模是 **8,000–15,000 行**。也就是说，MDM 有 85% 的代码在服务少数用户的长尾场景（某个站点、某种代理、某种桌面环境、某种语言）。

### 2.2 MDM 引擎的 8 个关键机制（Volant 要照此实现的部分）

这些是「快」的工程答案，逐条记录，作为 Volant 引擎的规格输入：

1. **Probe 复用**：首次请求用普通 `GET` 而非 `HEAD`，一次性拿到大小 / ETag / Last-Modified / 文件名 / 是否支持 Range，**并保留这条连接的响应体继续收数据**，省掉一次完整往返。启动实测 14 ms。
2. **动态分段规划器**（`planner.rs`，纯逻辑、无 I/O）：连接空闲时依次尝试 —— ① 认领未分配的段；② 抢占「下一条段还没收到首字节」的连接；③ 把**最大**剩余段对半切。切分从已认领位置量起，保证不会切进正在写的数据。`min_split = 12 KiB` 防止切碎。
3. **分段表 + 稀疏文件**：part 文件按 offset 写入（`pwrite`），体积即完整大小但不占实盘；崩溃续传只需保存段表。
4. **原子状态**：段表通过「临时文件 + rename」原子落盘，任何时刻被杀都能恢复，且**不记录未 flush 的字节**（快照 → flush → 写入的状态顺序）。
5. **慢连接丢弃**（`shed_slow`）：响应 2 秒后，若某连接速度 < 本下载历史最佳单连接的 1/4，且按它自己速度剩余工作 > 2 秒，则主动重连。**这是防止木桶效应**的关键。
6. **按主机学习并发上限**（`host_limits`）：被拒时记录「当时有几个连接正在收数据」，两次观测后生效为上限，10 分钟衰减。50 MiB / 限 2 连接的场景，MDM 只用 2 连接就完成，IDM 开了 480 个。
7. **磁盘与网络解耦**：每连接 256 KiB 缓冲，满缓冲或每 1 秒 flush 一次；全局最多 256 MiB 在内存中等待刷盘；**flush 期间不计入「连接变慢」**（否则慢盘会触发无谓重连）。
8. **限速 = 令牌桶**：所有连接共享一个桶，通过**延迟 socket 读**来让 TCP 反压服务器，而不是丢包。

**参数基线**（作为 Volant 的起点，需实测调整）：默认 8 连接、上限 32（可解锁 128）、初始分段 64 KiB、最小分段 12 KiB、每连接缓冲 256 KiB。

### 2.3 MDM 没做好的地方（= Volant 的机会）

| 问题 | 证据 | Volant 的回应 |
|---|---|---|
| **内存偏高** | 基准峰值 **106 MB**（1 GiB 文件）、空闲 100 MB | 目标空闲 ≤ 40 MB、下载 ≤ 80 MB |
| **UI 是 2005 年的形态** | 菜单栏 + 工具栏 + 分类树 + 12 列表格 + 状态栏，16 个常驻按钮 | 单列表 + 行内操作 + 详情面板 |
| **功能过载** | 60+ 功能，86 种语言，9 套主题 | 只保留 12 个核心功能 |
| **体积/依赖重** | 15 个 crate、reqwest/hyper/rustls/rquickjs 等 | 精简依赖树 |
| 分类是**手工**的 | 左侧树需要用户维护 | 按扩展名自动归类，零配置 |
| 多窗口 | 每个下载一个独立进度窗口 | 行内进度 + 侧边详情 |

## 3. 五步法拆解

### 第 1 步｜质疑要求

**要求 1「复刻 MDM 全部下载功能」**

- 提出者：你。目的推定：不想做出一个「功能残缺」的产品。
- 证据：MDM 的 125k 行里，核心下载引擎只占 11%。**「全部功能」的边际价值极低，边际成本极高**——torrent 是另一个协议栈（3.8k 行 + 独立 UI），debrid 需要三家付费账号，86 语言是机器翻译且仍在等母语者校对，9 套主题是给怀旧用户看的。
- 不执行的后果：你会失去 torrent 用户和「一站式」叙事。**这是唯一的真实代价**。
- 结论：**拆成「必须 / 延后 / 砍」三档**，见第 4 节裁决表。全量复刻与极简 UI 不可兼得。
- **你的决策（m00081）：torrent 是硬需求，必须 v1 有。** 本文档已据此修订。但「必须有」不等于「必须自己写」：BT 协议栈用 librqbit（Apache-2.0），一行协议代码都不写，只接它的事件与写盘；界面按「极简 torrent」收窄（第 5.3 节）。这样 torrent 的成本从「3–4 周独立协议栈」降到「1.5–2 周集成 + 界面」。

**要求 2「跑满带宽」**

- 目的：不想等。
- 证据：C1–C3 决定上限不在软件手里。**任何宣称「保证跑满」的产品都在撒谎**。可以做到的是：在带宽没被 ISP/服务器限制时，达到链路的 90%+。
- 结论：改成可验收的指标（第 6 节），并明确「服务器单 IP 限速时，多连接无效」这一物理事实。

**要求 3「资源占用极小」**

- 目的：不想让一个下载器拖慢电脑/占满内存。
- 追问：多小算小？MDM 的 106 MB 算「小」吗？对 32 GB 内存的机器无所谓，对 8 GB 的办公本很明显。
- 结论：必须量化（第 6 节），否则「极小」无法验收，也无法约束技术选型。

**要求 4「UI 极简、现代、美观、摒弃多余装饰」**

- 目的：不想用「上个时代的软件」。
- **与要求 1 直接冲突**：每个功能都需要入口，60 个功能不可能极简。MDM 的 16 个工具栏按钮不是设计失误，是功能过载的必然结果。
- 结论：**用户的意志必须在这里二选一**——要么功能完整但界面复杂，要么界面极简但功能收窄。本文档选择后者，理由：下载器的使用频率是「每次下载」，核心路径只有「粘贴链接 → 看进度 → 打开文件」三步，其余都是低频。

**要求 5「健壮、好维护」**

- 结论：这是**架构要求**，不是功能。具体化为：引擎与 UI 零耦合、状态可恢复、测试覆盖分段规划器的随机模拟、CI 跑端到端吞吐回归。

**关于「基于这个开源项目」的法律前提（必须澄清）**

MDM 是 **GPL-3.0-or-later**。两条路：

| 路径 | 含义 | 代价 |
|---|---|---|
| **A. Fork** | 直接改 MDM 的代码与 UI | 快（复用 125k 行）；但 **Volant 必须 GPL 开源**，且要背全部历史包袱（15 crate、86 语言、20+ 窗口） |
| **B. 独立实现** | 只借鉴设计思想与公开规格，代码从零写 | 慢；但许可证自由、体积/内存可控、可以真正极简 |

**本文档按 B 推进**。理由：A 路径下「极简 + 资源极小」两个目标都无法达成——你无法把一个 125k 行、100 MB 内存的程序删成一个新程序，那是重写，不是改造。架构思想（动态分段、稀疏文件、原子状态）属于通用工程知识，不构成侵权；但**代码一行都不能抄**。

### 第 2 步｜删除

见第 4 节完整裁决表。删除原则：

1. **能不做就不做**：debrid、视频、图库、远程控制、MCP、FTP 全部删除或延后；torrent 保留但**不自研协议**。
2. **能自动就不做界面**：分类、文件名、目录、更新检查全部自动。
3. **能藏就不摆**：常驻入口只有「添加」「暂停/继续」「打开目录」「删除」。
4. **删除前验证不可逆风险**：续传状态、已完成文件、用户设置——这三类数据**永不可丢**，宁可多写 100 行也不能省。

### 第 3 步｜简化

- 一个窗口（主列表 + 侧边详情），不是 20 个窗口。
- 一个存储文件（`state.json`，原子写），不是 JSON + SQLite + keychain + 注册表。
- 一种进度表达（行内细进度条 + 速度文字），不是 8 个 tab 的进度窗口。
- **两个引擎，一套基础设施**：HTTP/HTTPS（自研，核心价值）与 BitTorrent（librqbit，外部库）各自调度，但共用「状态落盘、队列、限速、事件通道、列表模型」这五件事。**不强行把两者抽象成一个调度器**——它们的源发现与校验模型差别太大，硬统一是过度设计。FTP 明确不支持并给出人话提示。
- 依赖最小化：`tokio` + `reqwest`（**必须 `default-features = false` + `native-tls`**，否则 reqwest 0.13 的 `default-tls` 会拉进 rustls + aws-lc-sys，在 windows-gnu 上要额外装 C 工具链且编译不稳）+ `serde` + `librqbit` + 一个 GUI 框架。**不引入** yt-dlp、7-Zip、QuickJS(PAC)、qrcodegen、brotli 等。

### 第 4 步｜加快周期

- 冷启动到可交互 ≤ 300 ms（MDM 实测 14 ms，它是 egui 无 WebView 的优势，要守住）。
- 「浏览器点下载 → Volant 开始下载」≤ 500 ms（扩展 → native messaging → IPC → 引擎）。
- 开发周期：引擎与 UI 可独立编译测试；**每周一个可运行版本**。

### 第 5 步｜自动化

只自动化稳定且重复的事：

- CI：`cargo test`（含分段规划器随机模拟）+ `clippy` + 端到端吞吐回归（自建 labserver，注入限速/丢包/无 Range）。
- 打包：一条命令产出安装包与便携版。
- **不**自动化：翻译、主题、发布文案。

## 4. 功能裁决表

图例：**P0** = v1 必须有；**P1** = v1 应有（可后置到 v1.1）；**P2** = 以后再说；**砍** = 明确不做。

| # | MDM 功能 | 裁决 | 理由 |
|---|---|---|---|
| 1 | HTTP/HTTPS 分段下载 + 动态再平衡 | **P0** | 核心 |
| 2 | 断点续传（崩溃/重启/断网） | **P0** | 核心可靠性，属于「不可逆数据」 |
| 3 | 磁盘空间预检、稀疏 part 文件 | **P0** | 防止写爆盘；稀疏写决定续传成本 |
| 4 | 重定向 / 等待页 / meta refresh / Range 探测 | **P0** | 没有它一半网站下载失败 |
| 5 | 按主机学习并发上限 + 慢连接让位 | **P0** | 「跑满带宽」的核心机制 |
| 6 | 浏览器捕获（Chrome/Edge/Brave/Vivaldi/Firefox） | **P0** | 下载管理器存在的最强理由 |
| 7 | 剪贴板监视 + 拖放 URL | **P1** | 低成本高感知 |
| 8 | 单文件限速 + 全局限速 | **P1** | 「别占满我看视频」 |
| 9 | 队列（并发数上限）、暂停/继续/全部暂停 | **P0** | 基础调度 |

## 5. v1 范围（做什么）

### 5.1 用户能做的三步

1. **给**：粘贴/拖入/浏览器捕获一个链接 → 自动探明文件名、大小、是否可续传 → 直接开始，**无二次确认弹窗**（除非重名）。
2. **看**：一行一个下载，显示文件名、大小、进度条、速度、剩余时间；多连接时能看到「正在用几个连接」。
3. **取**：完成后一键打开文件 / 打开所在目录；失败的给出人话原因和「重试」。

### 5.2 v1 明确不做

视频、图库、debrid、远程控制、MCP、Docker/NAS、FTP、自动解压、RSS 订阅、86 种语言（只做中/英）、主题系统、站点登录、网卡绑定、自动更新。

**产品要在 UI 上诚实地告诉用户这些不支持**，而不是假装支持。

### 5.3 「极简 torrent」的边界（重要的范围控制）

torrent 必须做，但**不复制 MDM 的 torrent 进度窗口**（它的 `progress-torrent.webp` 有「文件 / peer / tracker / piece 图」四个 tab）。Volant 的 torrent 只有三件事：

1. **添加**：粘贴 magnet、拖入 `.torrent`、或从浏览器捕获。
2. **选文件**：种子含多文件时，给一个可勾选的扁平列表（含「只下这几个」与「全部」）。
3. **看进度**：复用与 HTTP 下载**同一个列表行**——文件名、大小、进度、速度、做种状态。不做 peer 表、不做 tracker 表、不做 piece 方块图。

理由（第一性原理）：这些视图的存在是为了**调试 swarm 与优化分享率**，那是重度 BT 用户的需求，不是「把文件下下来」的需求。它们占据的界面面积与认知成本，远高于对 v1 用户的价值。

做种：**v1 默认「下完即停」，不自动做种**（不占用户上传带宽、不增加常驻内存）。设置里给一个「继续做种」开关 + 分享率上限，默认关。理由：做种是社区义务，但把上传流量作为**默认行为**强加给用户，与「资源占用极小」和隐私预期冲突；愿意分享的人自己打开。

> 注意：BEP-53 的「只下载选中文件」在多文件种子里会让未选文件缺失，做种时会因缺失 piece 而无法完整上传——这是 v1 的已知限制，UI 上说明即可。

**torrent 会话按需启动（这是「资源极小」与 torrent 能共存的前提）**

librqbit 的 Session 默认会开监听端口（触发 Windows 防火墙弹窗）、跑 DHT 节点、维护 peer 连接池——**这些是常驻成本，哪怕你没有 torrent 任务**。

所以 Volant 的规则是：**没有活跃 torrent 任务时，Session 完全不存在**。最后一个 torrent 完成/删除后，Session 被 drop（端口关闭、DHT 停止、内存归还）。HTTP 下载与空闲状态下的 Volant 不知道 BitTorrent 的存在。

M0 探针已确认这条路可行，`SessionOptions` 提供了三个开关：`dht: None`（完全不跑 DHT）、`listen: None`（不开任何 TCP/uTP 监听，不触发防火墙）、`disable_local_service_discovery: true`。三者叠加后，一个「只下不发」的会话对外零暴露。

这条同时解决了三个问题：空闲内存不因 torrent 变差、防火墙只在真正用 torrent 时提示、DHT 不在后台向全网暴露你的 IP。

### 5.4 信息架构（极简的具体形态）

```
┌──────────────────────────────────────────────────────┐
│  Volant                                    ＋  ⚙    │  ← 只有两个常驻按钮
├──────────────────────────────────────────────────────┤
│  ubuntu-24.04.iso        6.0 GB  ████████░░  1.2 MB/s│
│  holiday-photos.zip     64 MB   ██████████  完成     │
│  debian-13-netinst.torrent 780 MB  ██████░░░░  3.1 MB/s│
├──────────────────────────────────────────────────────┤
│  选中行详情：8 连接 · 服务器 日本 · 剩余 12:04         │
│  torrent 行为：12 peer · 做种比 1.4 · 剩余 4:10        │
└──────────────────────────────────────────────────────┘
```

**torrent 不是第二个界面**：它只是列表里的一种行，详情面板换一组字段（连接数 → peer 数，服务器国家 → 做种比）。这是「同一列表」的硬约束——若发现需要给 torrent 开独立窗口，说明 5.3 的边界被突破了。

- 无菜单栏、无工具栏、无分类树、无状态栏、无表格线。
- 行内 hover 才出现操作（暂停/删除/打开），平时不可见。
- 设置是一个两栏对话框，不是 6 页 tab。
- 颜色取自图标：`#0B0C0E` 近黑 + 纯白 + 一个强调色（建议电光蓝或图标同源的中性灰，待设计稿定）。
- 动效只用在两处：进度条平滑插值、列表增删的位移。**不做**装饰性动画。

## 6. 验收标准（可测，不可协商）

### 6.1 吞吐（「跑满带宽」的操作化定义）

| 场景 | 条件 | 通过标准 |
|---|---|---|
| T1 本地基线 | 127.0.0.1 labserver，10 GiB 单文件 | 吞吐 ≥ **同机同条件裸写基线 × 80%**（基线做法见下） |
| T2 模拟宽带 | netem：100 Mbps、20 ms RTT、0.1% 丢包 | ≥ **90 Mbps**（链路 90%） |
| T3 单连接对照 | 同上，但只允许 1 连接 | 记录为基线，用于证明多连接收益 ≥ 3× |
| T4 服务器限连接 | 限 2 连接，各 2 MB/s | 用满 2 连接，完成时间 ≤ 理论值 110% |
| T5 连接抖动 | 每 2 条连接传 2 MiB 后被切断 | 完成时间 ≤ 无故障场景 1.8× |
| T6 慢盘 | 限速写盘 50 MB/s | 不误判慢连接，不额外重连，吞吐 = 50 MB/s |
| T7 torrent 吞吐 | 热门公共种子（Ubuntu ISO，peer 充足），500 Mbps 链路 | ≥ 链路 60%（BT 受 swarm 质量决定，不承诺 90%） |
| T8 torrent 多任务 | 3 个活跃种子，各 limit 100 peer | 互不饿死，总吞吐 ≥ 单任务独跑的 80% |

> 说明：T2 的 90% 是**软件能力上限**。真实宽带若达不到，第一嫌疑是 ISP/服务器，第二才是软件。文档不承诺「任何网站都跑满」。

> **T1 为什么用比值而不是绝对数字**（2026-11-10 改，M1 实测后）：原来写「≥ 1.5 GB/s」。测下来这个数字量的是**盘当时的缓存状态**，不是引擎：同一台机器、同一份代码，静置 5 分钟后跑是 1686 MB/s，连着跑第三遍掉到 1076 MB/s；裸写对照同样是 1743 → 1552 → 1397（写穿 SLC 缓存后降速）。所以 T1 改成比值，且规定基线必须**同机同条件**：
>
> 1. 静置 5 分钟（让 SSD 缓存恢复），
> 2. 裸写 10 GiB + fsync（`tools/rawwrite.py`），记吞吐 A，
> 3. 引擎跑同一个 10 GiB（`bench t1`），记吞吐 B，
> 4. 紧接着再裸写一次，记吞吐 C，
> 5. 判据：**B ≥ 80% × (A+C)/2**；绝对值（B、基线）照实记录，不作判据。
>
> 80% 是留给「8 条连接 + 状态落盘 + 稀疏文件记账」的工程余量；本机实测 112%（1823 vs 1630）。换机器不用改目标。

> **T2 的条件在本机做不到，用 labserver 仿真**（2026-11-10 补，M2 实施时确认）：Windows 没有 netem，也没有可用的丢包/延迟注入驱动。所以 T2 在 `volant-labserver` 上用三个开关拼出来：`grate=12.5M`（全网共享 100 Mbps 容量）、`delay=20`（每请求先等一个 RTT）、`stall_every=1460K,stall=20`（0.1% 丢包 × 1460 B 段 ≈ 每 1.46 MB 卡一次，代价按快速重传的一个 RTT 算，不按 RTO 的 200 ms）。**没仿真 TCP 拥塞窗口**，等于假设 cwnd 已经够大——这个仿真是**偏乐观**的，报告里必须写明。判据不变：≥ 90 Mbps。

> **T6 的判据拆成两条可测量的**（2026-11-10 补，M2 实施时确认）：
>
> 1. 吞吐 ≥ 50 MB/s 的 95%（写成「= 50 MB/s」量不出来，任何实现都有 probe、收尾 fsync、rename 的固定开销）；
> 2. **不额外重连**用服务端请求计数做硬证据：同一份文件先全速跑一次、再限速跑一次，限速那次的 `GET /file` 请求数不得多于全速那次。
>
> 第 2 条是**对比判据**而不是「请求数 = 连接数」：planner 分段/抢占本身就会重发（owner 的下一个 chunk 会越过被切走的切点），小文件上量到 27–39%，这与慢盘无关。修它要改 planner 的切分逻辑，记在 M3 待办里。

### 6.2 资源

| 指标 | 目标 | 上限（不可超） |
|---|---|---|
| 空闲内存（RSS） | ≤ 110 MB | 130 MB |
| 8 连接下载峰值内存 | ≤ 130 MB | 160 MB |
| torrent 3 种子峰值内存 | ≤ 150 MB | 190 MB |
| 空闲 CPU | ≤ 0.1% | 0.5% |
| 1 Gbps 下载 CPU | ≤ 同机 `curl --limit-rate 125M` 同条件 × 1.25（本机 = 33% 单核） | 50% 单核 |
| 冷启动到可交互 | ≤ 300 ms | 600 ms |
| 安装包 | ≤ 12 MB | 18 MB |
| 常驻进程数 | 1 | 2（ext host 除外） |

> **v0.3 修订（M0 实测后，2026-11-10）**：原值写的是空闲 ≤ 35 MB / 峰值 ≤ 70 MB，那是在写文档时凭「原生程序」的直觉估的，**测出来才知道 GPU 加速的 UI 一开进程就吃掉 90–120 MB**。三个框架在 780×470 窗口、1000 行列表下实测：egui ws 119.7 MB / private 65.9 MB，Slint 98.7 / 52.8，MyGo 90.8 / 106.0。作为交叉验证，MDM 自己的基准记录 egui + D3D12 的**峰值** 106.2 MB，而 IDM（GDI 原生控件）只有 46.3 MB。
>
> 结论：**约 100 MB 是 GPU 加速 UI 的进程内存底线**（驱动 DLL 映射 + 显存映射 + 字体 atlas + 双缓冲），不是实现粗糙。压到 35 MB 只剩原生控件（锁死 Windows）或 CPU 光栅化（控件全自研）两条路，与决策 3、决策 4 冲突。你已确认接受修订后的数字（m00884）。
>
> 这条修订本身是个教训：**资源指标只有在目标框架上量过才算数**。今后凡是「估算」出来的验收值，都要标注来源，不许当成约束用。

> **v0.6 实测（M4 收尾，2026-11-11）**：空闲 RSS 107.8 MB、8 连接峰值 120–121 MB、空闲 CPU ≈0%、冷启动 114–165 ms、exe 7.32 MB（无安装器）全部达标；**「1 Gbps 下载 CPU」实测 46% 单核，未达 25% 目标**（上限 50% 也贴着）。同条件下 `curl --limit-rate 125M` 只要 20.5%，服务端限速到同样吞吐时我们只要 31.5% —— 也就是说「以 1 Gbps 收+写」本身约 31.5%，客户端限速器再叠加约 22 个百分点（15.6 ms 定时器把平滑限速量化成突发）。优化要动 `limiter.rs` 的发放节拍与写盘形态，放进 M5。详见 `docs/m4/REPORT.md` §5。

> **v0.7 修订（M5 实测后，2026-11-11）：1 Gbps CPU 从绝对值改成比值口径。**
>
> M5 把 46% 修到 **33%**（app 30.8 / 34.1，CLI 32.7 / 33.2 / 33.6，125.0 MB/s 吞吐不变；手法是把限速器改为「攒够 512 ms 额度才睡一次」，曲线见 `docs/HANDOFF.md` §6）。剩下的 8 个点不是我们的代码：同链路同磁盘下 `curl --limit-rate 125M` **28.6%**（4.72 s / 16.48 s；更早一次读到 27.5%），把引擎换成「裸 `reqwest` chunk 循环」（`crates/engine/examples/recvonly.rs`，无分段、无写盘队列、无记账）CPU 与引擎相同（1.61 vs 1.63 s / 512 MiB），**不限速搬运下限 1.14 ns/B**。也就是说「以 125 MB/s 收包并写盘」在这台机器上本身就要 28–33%，绝对数字量的是机器而不是代码。
>
> 因此这一行改为 **≤ 同机同条件 curl × 1.25**，与 6.1 的 T1（≥ 同机裸写基线 × 80%）同一思路：换台快机器指标自动变严。本机判据 = 4.72 × 1.25 = **5.9 s / 2 GiB = 33%**；上限 50% 不变。用户已确认（m00501）。

> **v0.8 实测（M5 收尾，2026-11-11）：浏览器捕获落地，捕获链路达标。**
>

### 6.3 健壮性

- `kill -9`（或任务管理器结束进程）后重启，**已完成字节不重下**，丢失 ≤ 1 MiB。
- 磁盘满：停止并保留状态，给出「需要 X GB」的提示，**不删除 part 文件**。
- 断网 10 分钟恢复：自动续传，无需用户操作。
- 重名文件：`(1)` 后缀，绝不覆盖已有文件。
- 状态文件损坏：降级为「从头下载」，而不是崩溃。

### 6.4 UI

- 核心路径 ≤ 2 次点击（捕获 → 完成）。
- 键盘：`Ctrl+V` 添加、`Space` 暂停/继续、`Del` 删除；`Enter` 打开详情，已完成任务打开文件。
- 并发：同时下载最多 20 个任务，每任务连接数最多 32。
- 无障碍：所有控件可 Tab 到达、有可见焦点环、对比度 ≥ 4.5:1。
- 100% DPI 到 200% DPI 不破版。

## 7. 技术选型

语言：**Rust**（无争议——性能、内存安全、单二进制、无运行时；且本机已有 `rustc 1.99.1`）。

### 7.1 UI 层：已定 egui 0.37（M0 四方案实测）

原文档在此处列了五个方案、给了一堆估算内存，并建议选 Slint。**M0 把四个能跑的方案都写了原型、在同一台机器上用同一套视觉规格（1000 行列表 / 行高 52 / 同一套假数据）实测**，结论与当时的估算不一致——所以以实测为准。

| 指标 | egui 0.37 | Slint 1.18.1 | MyGo 0.8.3 | gpui 0.2.2 |
|---|---|---|---|---|
| 实现语言 | Rust | Rust + DSL | **Go** | Rust |
| 许可证 | MIT / Apache-2.0 | **GPL-3.0 或商业** | MIT | Apache-2.0 |
| exe 体积 | **5.62 MB** | 9.99 MB | 10.58 MB | 未构建 |
| 冷启动 | 162.3 ms | 159.4 ms | **70.0 ms** | 未构建 |
| private 内存 | 65.9 MB | **52.8 MB** | 106.0 MB | — |
| working set | 119.7 MB | 98.7 MB | **90.8 MB** | — |
| 线程数 | 10 | 11 | 47 | — |

**选 egui，四条理由**：①许可证唯一无争议（Slint 拖 GPL/商业授权，与「不一定开源」冲突；gpui 虽 Apache 但 pre-1.0）②体积最小 5.62 MB，且同进程内共享 tokio 与 reqwest，不再加运行时 ③private 内存次优，160 ms 启动已在人眼「瞬时」内 ④像素级控制最直接——极简 UI 要精确控制行高、进度线、对齐，egui 直接画矩形，Slint 要在 DSL 里搏斗。

**被否掉的两个**：

- **Slint** 视觉与内存都合格，但它赢了 15 MB private 内存，代价是 GPLv3 传染（要么开源、要么买商业授权）。这个交易不值。
- **MyGo** 启动 70 ms 最快（retained + GPU 直绘的收益），但它是 **Go 框架**——选它意味着要么用 Go 重写整个引擎（放弃 tokio/reqwest/librqbit，「跑满带宽」的生态全没了），要么 Go UI + Rust 引擎走 FFI 双运行时，两者都违背「资源极小」「健壮好维护」。另外它的 `List` 默认把选中行整行填成强调色（连状态列都看不清），要绕开只能放弃 `Rows` 快捷方式自己画。
- **gpui** 视觉与 Zed 同级，但构建期强制要求 `fxc.exe`（Windows SDK 的 HLSL 编译器，`gpui-0.2.2/build.rs:356`）。本机无 MSVC/SDK，试过完整 SDK（下载停滞）、`Microsoft.Windows.SDK.BuildTools`（21.7 MB，不含 fxc）、`Microsoft.Windows.SDK.CPP.x64`（50.5 MB，不含 fxc）三条路都失败——fxc 只随完整 Windows SDK 的图形工具集分发。一个连编译都要装 1.3 GB SDK 的框架，与「健壮、好维护」背道而驰。

详细实测记录见 `docs/m0/REPORT.md` 第 7 节，四张原型截图在 `docs/m0/`。

> **注意**：UI 实现推迟到 M4（见第 8 节）。框架已定为 egui，但**先让引擎跑通并拿到 T1/T2/T4/T5 数据**，UI 再落地——避免在引擎还没证明「跑满带宽」之前先花两周画界面。

### 7.2 其余选型（低风险，可直接定）

| 层 | 选择 | 理由 |
|---|---|---|
| 异步运行时 | `tokio`（多线程） | 事实标准 |
| HTTP | `reqwest` **`default-features = false`** + `features = ["native-tls","charset","system-proxy"]` | Windows 走 schannel，零 C 编译、用系统证书库；**不能用默认的 rustls**——`reqwest 0.13` 的 `default-tls = ["rustls"]`，而 `rustls` feature 指向 `__rustls-aws-lc-rs`，会拖进 aws-lc 的 C 构建与 jitterentropy 崩溃 |
| DNS | 系统解析 + 自建缓存 | 省掉 hickory 依赖 |
| 序列化 | `serde_json` | 状态文件人可读 |
| 原子写 | 自实现「临时文件 + rename」 | 30 行，不值得引入依赖 |
| 日志 | 自写滚动文件 | 不做崩溃转储 |
| 浏览器扩展 | Chromium MV3 + Firefox，单一代码库 | 复用 MDM 的公开结论（不抄代码） |
| Native messaging | **独立 `volant-host.exe`**（M5 改；原定 `--nm-host` 子命令） | 浏览器清单只能写一个 exe 路径、**不能带参数**，拉起时没有 argv；366 KB 的第二个入口比 launcher 干净 |
| BitTorrent | `librqbit` **9.1.0（pin 精确版本）** | Apache-2.0，可闭源商用；协议栈零自研；仅用 library API，**不用**它自带的 HTTP API 与 Web UI |

**librqbit 集成的 4 个真实风险（M0 已实测，结论见下）**

1. **API 稳定性**：9.x 是活跃大版本，破坏性改动频繁。→ `Cargo.toml` 里 `=9.1.0` 精确锁定，升级前跑一遍 torrent 回归。**M0 结论：编译通过。**
2. **runtime 冲突**：`Session::new(folder) -> BoxFuture<'static, Result<Arc<Self>>>`（`librqbit-9.1.0/src/session.rs:561`）、`new_with_opts`（575）都是 `async move`，在调用者 tokio runtime 上跑，**不自建 runtime。M0 结论：无冲突。**
3. **写盘层**：`SessionOptions::default_storage_factory: Option<BoxStorageFactory>`（session.rs:452）可替换。**M0 结论：可接自研 sparse + 状态文件。**
4. **二进制体积**：**M0 实测 +8.66 MB**（`rq-spike.exe` 9.07 MB − `tokio-base.exe` 0.41 MB），而不是原先估计的 1.5–2.5 MB，差 3.5 倍。BT 协议栈本身重：DHT、uTP、tracker、bencode、peer 协议、加密、fastresume。→ 接受这个成本；安装包用 LZMA 压缩后约 +3–4 MB，仍在 12 MB 预算内。若将来超预算，第一刀砍 UPnP 与 uTP。

**构建前置条件（windows-gnu 上必做，否则 aws-lc-sys 编不过）**：`AWS_LC_SYS_NO_JITTER_ENTROPY=1`，且 `TMP`/`TEMP`/`TMPDIR` 指向工作区可写目录（本机子进程写 `%TEMP%` 会被拒）。详见 `docs/m0/REPORT.md` 第 5 节。
